## Root causes

1. Both implementations performed launch side effects before persisting the replacement session. The JS exception also bypassed watcher attachment. Retrying the CLI could therefore launch a duplicate task.
2. The old lock protocol created the shared lock before writing its owner JSON. ENOSPC/crash could leave an empty or truncated file. Its stale check could not parse that file, so future writers waited until the 30-second timeout indefinitely.
3. The database itself was overwritten in place. Even with a prelaunch reservation, a partial final write could destroy the reservation. The fix must make the database replacement atomic too.
4. Long snapshot operations amplify the opportunity for failure. Inspection of store writers did not establish that a store lock was actually held over a ten-minute `docker commit`; the launch flow now explicitly reserves and releases before all Docker operations.

## Reproduction and verification

Run `bun test ./js/test/regression-193.js` and `cd rust && cargo test --test regression_193`; Rust's `atomic_write` unit test injects a partial ENOSPC-equivalent write. JS reproduces the actual prelaunch/postlaunch ordering and failures with injected runner/store operations. These tests never fill the host disk. Before the atomic DB fix, the partial-write regression lost the reserved record; after it, the same record survives.

For an older installation, an empty `executions.lock` with an old mtime blocks writes; a save error after a successful `docker run` leaves the old session record. Workarounds are to stop concurrent recovery, inspect Docker by name family, and remove an abandoned malformed lock only after checking that no store writer owns it. Serializing large snapshots and discarding regenerable caches reduces disk pressure, but does not repair tracking semantics.

The separate downstream storage design (#2889) should prefer an in-place command handoff before `docker start`, serialize unavoidable snapshots, preflight disk headroom and clean obsolete snapshot artifacts. This PR fixes start-command's tracking failures without automatically deleting users' retained containers or build data.
