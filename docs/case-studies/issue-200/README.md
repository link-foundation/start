# Issue #200: safe execution-log uploads

[Issue #200](https://github.com/link-foundation/start/issues/200) reports that manual execution-log uploads publish raw command output. This is implemented with equivalent protections in JavaScript and Rust in [PR #204](https://github.com/link-foundation/start/pull/204).

## Evidence and timeline

- 2026-05-20 18:48 UTC: commit `38d1fe4` introduced `--upload-log`; both implementations sent the stored log path directly to `gh-upload-log`.
- 2026-05-20 18:59–19:04 UTC: commits `bb5f373` and `c0f823c` improved Windows shim handling and command resolution. Neither added a publication sanitizer.
- 2026-10-10 09:30 UTC: issue #200 documented the raw-token reproduction and the alternate sanitizing uploader used by hive-control-center. The downloaded issue has no comments, linked uploaded logs, or image attachments.
- This investigation reproduced disclosure entirely locally with a fake uploader: `secretLeaked=true`, `uploadedOriginal=true`, `explicitlyPrivate=false`. After the fix those values are `false`, `false`, and `true`. No credentials or logs were actually published during reproduction.
- An audit found equivalent raw uploads in both automatic failure handlers. Those handlers also forced `--public` and inserted the original command into an issue title/body. They are covered by the same fix.

Evidence is archived in [data](data/). The issue snapshot replaces the issue author's complete fake GitHub token with `[REDACTED EXAMPLE TOKEN]`; otherwise its content and metadata are preserved. Upstream source snapshots retain their GitHub API metadata and content SHA, and are accompanied by decoded text for review. Test fixtures assemble fake tokens at runtime so source evidence and tests do not look like live credentials to repository scanners.

Three integration regressions were found and reproduced before finalizing. Overlapping tokens at a block boundary must retain a containing authorization header's broader continuation state, or later words on the same header can escape redaction. The CLI's Docker `options.env` array must never replace the active process environment used to discover secrets. Quoted AWS assignments must include their values in the match instead of stopping at the opening quote. Dedicated tests cover each; their pre-fix output is archived alongside passing validation. Format tests assert that the sensitive value itself disappears, including values nested in a header, URL, or assignment.

## Implementation details and limits

Each sanitizer works on bytes so multibyte UTF-8 and invalid input bytes survive unchanged outside redactions. The holdback is at least 2048 bytes and at most 64KiB, sufficient for bounded token prefixes, JWT checks, and exact environment values. Unbounded recognized tokens and header values switch into a continuation state, discard their suffix until a delimiter, then resume ordinary output. A credential-like uninterrupted word of 512 or more bytes is conservatively redacted; this keeps unusual giant JWT segments safe without retaining an entire line. Overlapping matches are merged before replacement, preventing an inner token or shorter known secret from exposing another secret's suffix.

Known environment values longer than 64KiB block publication instead of increasing memory without a limit. Empty values are ignored. The default Rust path reads Unix environment values as bytes, including values that cannot be decoded as UTF-8. Temporary copies are cleaned on normal completion and failed uploads; the original log and recorded command remain local and unchanged.

The guarantee covers maintained formats and active conventional secret environment values. No pattern-based sanitizer can identify every arbitrary unknown password or every deliberately encoded credential. The explicit opt-out publishes raw log contents and must therefore be intentional. Private upload visibility is a second safeguard: GitHub documents that secret gists remain accessible to anyone holding their URL. [GitHub gist documentation](https://docs.github.com/en/get-started/writing-on-github/editing-and-sharing-content-with-gists/creating-gists)

## Existing components and reuse assessment

[hive-mind's token sanitizer](https://github.com/link-assistant/hive-mind/blob/main/src/token-sanitization.lib.mjs) combines maintained credential rules, known local tokens, Secretlint, and a residual publication scan. Its worker module delegates bounded block processing to a streaming module and uses worker heap limits for large files. The modules also import hive logging, telemetry, command discovery, runtime bootstrap, and encoded-credential helpers. Directly importing those application modules would add unrelated runtime assumptions and would not provide Rust parity. Extracting the dependency-free core into a maintained shared package is a useful future option; consistent byte-stream rules and regression fixtures provide a migration boundary. [Upstream worker source](https://github.com/link-assistant/hive-mind/blob/main/src/log-sanitize-worker.lib.mjs)

[Secretlint](https://github.com/secretlint/secretlint) supplies pluggable credential detection and could provide a second publication gate, but a detector does not itself implement bounded sanitized-file staging or Rust integration. This implementation needs no scanner installation or network access to prepare logs.

[Gitleaks](https://github.com/gitleaks/gitleaks) supports files, repositories, and stdin scanning. It is suitable as an additional validation gate; its `--redact` option redacts its own reports and stdout rather than producing the sanitized source file required here. Adding a subprocess would require deployment and consistent scan-failure handling in both runtimes.

[gh-upload-log](https://github.com/link-foundation/gh-upload-log) already supplies private visibility and large-file strategies. Its documented `GH_UPLOAD_PUBLIC` environment setting is why callers pass `--private` explicitly, rather than trust an implicit default. The existing uploader installation, path resolution, Windows shell handling, inherited interactive output, and upload exit statuses are preserved. [GitHub CLI](https://cli.github.com/manual/gh_gist_create) likewise defaults gists to secret visibility, but visibility does not replace sanitization.

## Reproduction and validation

From the repository root:

```sh
bun experiments/issue-200/reproduce-upload.js
bun test ./js/test/log-sanitizer.js ./js/test/failure-handler.js
node --test js/test/log-sanitizer.js
cargo test --manifest-path rust/Cargo.toml --test log_sanitizer --test failure_handler
node --max-old-space-size=96 experiments/issue-200/large-log.js
bash experiments/issue-200/large-log-rust.sh
```

The finite large-file fixture is 115,343,360 bytes (110MiB). Node sanitized it in 16.4 seconds with maximum RSS 89,012KiB under a 96MiB old-generation limit; the uploaded-copy scan found no assembled fake token. Rust sanitized the same finite fixture in 29.6 seconds under a 256MiB process address-space limit, also without leaking the fake token. These are local measurements, not cross-platform performance guarantees. Test and experiment output is preserved in `data/`.
