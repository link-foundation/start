# Case study: JavaScript-first CI, behavioral parity and bounded native builds

Issue: [start#197](https://github.com/link-foundation/start/issues/197). Implementation is part of [start#204](https://github.com/link-foundation/start/pull/204), alongside #198–#202. The complete issue, standard, comments, upstream contracts, CI snapshots and relevant failed/cancelled logs are preserved in `data/` and `logs/`.

## Findings and sequence of events

The JavaScript and Rust workflows independently accepted pushes and PR events, with separate language path filters. There was no dependency edge between them. Rust security scans also ran independently in `security.yml`, so gating only the Rust test workflow would leave two additional bypasses. The pipeline aggregator allowed cancelled PR jobs to produce a successful status. A test-count threshold measured quantity, but did not bind a feature to matching native behavior.

The source tree had no semantic generation mapping, inventory of manual adapters, shared fixtures, compilation load controls or collaboration instructions. Target directories were cached across changed dependency graphs with broad fallback keys. Every check could cancel main. The main branch had no protection (`branch-protection-before-error.txt`, `rulesets-before.json`). These observations explain the process gaps; the historical failures have their own concrete causes and are not attributed to parity solely because both workflows ran.

## Components and primary research

The selected dependency graph is based on GitHub's [reusable workflow rules](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations): a relative reusable call uses the caller's commit and inherits its GitHub event context. Distinct callee concurrency names avoid cancellation collisions from inherited `github.workflow`. [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) explains `needs` and success gating. These properties preserve push/manual release behavior while removing the independent Rust entry.

Alternatives considered: `workflow_run` requires deliberate same-SHA checkout and separate event handling; `dorny/paths-filter` still needs complete path coverage; `Swatinem/rust-cache` is useful for native projects but a stale target cache is counterproductive for this issue's bounded-artifact requirement; `cargo-sweep` can prune shared developer targets but was unnecessary after adopting a single explicit budget and fresh CI targets. Bun's existing YAML parser and `node:test` avoid adding a YAML or snapshot-test dependency. The existing CodeQL, native actionlint and zizmor checks were retained.

Cargo's [profile documentation](https://doc.rust-lang.org/cargo/reference/profiles.html), [build-cache explanation](https://doc.rust-lang.org/stable/cargo/reference/build-cache.html) and [configuration reference](https://doc.rust-lang.org/stable/cargo/reference/config.html) establish what debug, incremental, jobs and target settings actually control. [GitHub ruleset API](https://docs.github.com/en/rest/repos/rules), [deploy-key documentation](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys) and [environment deployment restrictions](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments) support the protection/release design. No unscoped personal token was stored as a release credential.

## Protection scope and operational limits

The ruleset bypass applies to repository deploy keys, not to arbitrary GitHub Actions runs. At setup the repository had no keys; the only added key is release key `166030970`. Its secret metadata and main deployment branch restriction are saved, while private bytes were never printed or committed and temporary files were unlinked. Only main version-writing jobs receive the environment; default `GITHUB_TOKEN` remains the API credential for release metadata. Adding another writable deploy key would expand the bypass and requires repository administration review.

SSH release version pushes can trigger normal main CI, unlike the old GITHUB_TOKEN suppression. They preserve the existing version commit flow and bring those commits under validation. Existing shared main writer serialization and freshness checks prevent parallel release commits. No merge or publication is performed by this issue-solving task itself.
